# Requirements Document

## Introduction

**Feature:** `youth-benefit-frontend`

청년 사용자가 자신의 나이, 지역, 소득, 취업 상태, 주거 형태를 입력하면 조건에 맞는 정책을 찾아 카드로 확인하고, 정책별 추천 이유와 질의응답을 이용할 수 있는 모바일 우선 단일 페이지 프론트엔드를 제공한다.

## Scope

### 2.1 포함 범위

- 정책 검색 입력 폼
- `./policies.json` 로드 및 내장 샘플 정책 대체
- 브라우저 내 정책 조건 필터링
- 검색 결과 요약과 정책 카드
- 정책별 추천 이유 API 연동 및 대체 문구
- 정책별 질문 API 연동
- 알림 신청 토스트
- 모바일 우선 반응형 디자인과 접근성

### 2.2 구현 경계

- 최종 구현은 오직 `frontend/index.html`만 수정해야 한다.
- HTML, CSS, JavaScript는 `frontend/index.html` 한 파일에 통합해야 한다.
- `frontend/policies.json`, `lambda/handler.py`를 포함한 담당 외 파일은 수정하거나 생성하지 않아야 한다.
- 로그인, 데이터베이스, 실제 알림 등록·저장·전송은 구현 범위에 포함하지 않는다.
- 외부 라이브러리는 사용하지 않거나 최소화해야 하며, Noto Sans KR 웹 폰트 링크는 허용한다.

## Glossary

- **사용자 조건**: 나이, 지역, 소득, 취업 상태, 주거 형태로 이루어진 입력값 집합.
- **정책**: `id`, `name`, `minAge`, `maxAge`, `regions`, `maxIncome`, `employment`, `housing`, `benefit`, `deadline`, `url`을 포함하는 객체.
- **매칭 정책**: 모든 필터 조건을 동시에 만족하는 정책.
- **추천 이유 API**: `mode: "explain"` 요청을 처리하는 `API_URL` 엔드포인트.
- **질문 API**: `mode: "ask"` 요청을 처리하는 `API_URL` 엔드포인트.
- **대체 추천 이유**: 정책의 `reason` 값이 있으면 그 값을 사용하고, 없으면 `나이·지역·소득 조건이 일치합니다`를 사용하는 처리.
- **안전한 DOM 렌더링**: 사용자 입력, 정책 데이터, API 응답을 HTML 문자열로 실행하지 않고 텍스트 노드 또는 동등하게 안전한 방법으로 표시하는 처리.

## Requirements

### 요구사항 1. 단일 파일 구성과 API 설정

**사용자 스토리:** 개발 담당자로서, 해커톤 MVP의 담당 범위를 벗어나지 않도록 프론트엔드를 하나의 파일에서 관리하고 싶다.

#### 인수 조건

1. 최종 구현 시 시스템은 HTML, CSS, JavaScript를 모두 `frontend/index.html` 안에 포함해야 한다.
2. 최종 구현 시 시스템은 JavaScript 코드 최상단에 다음 선언을 문자 단위로 정확히 포함해야 한다: `const API_URL = "";`.
3. 시스템은 `API_URL` 선언보다 앞에 다른 JavaScript 실행문 또는 선언을 두지 않아야 한다.
4. 최종 구현 시 `frontend/index.html` 이외의 기존 파일을 수정하거나 새 담당 외 파일을 생성하지 않아야 한다.

### 요구사항 2. 정책 데이터 로드와 샘플 대체

**사용자 스토리:** 사용자로서, 정책 데이터 파일을 사용할 수 없는 시연 환경에서도 정책 검색 기능을 확인하고 싶다.

#### 인수 조건

1. 페이지가 초기화될 때 시스템은 상대 경로 `./policies.json`에서 정책 데이터를 `fetch`해야 한다.
2. 시스템은 JavaScript 내부에 정확히 3개의 정책 객체로 이루어진 `SAMPLE_POLICIES`를 포함해야 한다.
3. `SAMPLE_POLICIES`의 각 객체는 정책 카드 표시와 필터링에 필요한 정책 필드를 포함해야 한다.
4. `./policies.json` 요청이 실패하거나, 파일이 없거나, JSON 해석이 실패하거나, 해석 결과가 배열이 아니거나, 배열이 비어 있으면 시스템은 `SAMPLE_POLICIES`를 정책 데이터로 사용해야 한다.
5. `./policies.json`이 비어 있지 않은 배열로 정상 로드되면 시스템은 해당 배열을 정책 데이터로 사용해야 한다.
6. 정책 데이터 로드 실패는 페이지 전체의 입력 및 검색 기능을 중단시키지 않아야 한다.

### 요구사항 3. 사용자 조건 입력

**사용자 스토리:** 청년 사용자로서, 내 상황을 입력하여 받을 수 있는 정책을 찾고 싶다.

#### 인수 조건

1. 시스템은 나이를 입력할 수 있는 숫자 입력 필드를 제공해야 한다.
2. 시스템은 지역을 `서울`, `경기`, `인천`, `부산`, `기타` 중 하나로 선택할 수 있게 해야 한다.
3. 시스템은 만원 단위 소득을 입력할 수 있는 숫자 입력 필드를 제공해야 한다.
4. 시스템은 취업 상태를 `재직`, `구직`, `학생` 중 하나로 선택할 수 있게 해야 한다.
5. 시스템은 주거 형태를 `월세`, `전세`, `자가`, `부모님집` 중 하나로 선택할 수 있게 해야 한다.
6. 시스템은 정책 검색을 실행하는 명확한 찾기 CTA를 제공해야 한다.
7. 사용자가 찾기 CTA를 실행했을 때 필수 입력이 유효하지 않으면 시스템은 검색을 실행하지 않고 해당 문제를 한국어로 식별 가능하게 안내해야 한다.
8. 입력 컨트롤과 버튼은 연결된 레이블, 키보드 조작, 식별 가능한 포커스 표시를 제공해야 한다.

### 요구사항 4. 정책 조건 매칭

**사용자 스토리:** 사용자로서, 입력한 모든 조건을 만족하는 정책만 결과로 보고 싶다.

#### 인수 조건

1. 사용자가 유효한 조건으로 찾기를 실행하면 시스템은 프론트엔드 JavaScript에서 정책 목록을 필터링해야 한다.
2. 정책은 `policy.minAge <= user.age <= policy.maxAge`를 만족해야 나이 조건과 일치한다.
3. 정책의 `regions`가 `전국`을 포함하거나 사용자가 선택한 지역을 포함해야 지역 조건과 일치한다.
4. 정책의 `maxIncome`이 `null`이거나 `user.income <= policy.maxIncome`이어야 소득 조건과 일치한다.
5. 정책의 `employment`가 사용자가 선택한 취업 상태를 포함해야 취업 상태 조건과 일치한다.
6. 정책의 `housing`이 사용자가 선택한 주거 형태를 포함해야 주거 형태 조건과 일치한다.
7. 시스템은 나이, 지역, 소득, 취업 상태, 주거 형태 조건을 모두 동시에 만족하는 정책만 매칭 결과에 포함해야 한다.
8. 시스템은 찾기를 다시 실행할 때 이전 결과를 새 매칭 결과로 교체해야 한다.

### 요구사항 5. 검색 결과 요약과 정책 카드

**사용자 스토리:** 사용자로서, 받을 수 있는 정책 수와 각 정책의 핵심 정보를 빠르게 확인하고 싶다.

#### 인수 조건

1. 매칭이 완료되면 시스템은 매칭된 정책 수를 숫자로 강조한 한국어 결과 요약을 표시해야 한다.
2. 매칭된 각 정책에 대해 시스템은 별도의 카드를 표시해야 한다.
3. 각 카드는 정책 이름, 혜택, 마감일까지의 D-day, 정책 링크, 알림 버튼을 표시해야 한다.
4. 시스템은 정책의 `deadline`을 기준으로 현재 날짜와의 일수 차이를 계산해 D-day를 표시해야 한다.
5. 마감일까지 남은 날이 0일 이상 7일 이하이면 시스템은 D-day 요소에 `--lime` 색상을 사용해야 한다.
6. 정책 링크는 유효한 안전한 URL인 경우에만 이동 가능한 링크로 제공하고, 새 창을 사용한다면 `noopener noreferrer` 보호를 적용해야 한다.
7. 매칭 정책이 없으면 시스템은 결과 수가 0임을 알리고 빈 카드 목록을 표시해야 한다.

### 요구사항 6. 추천 이유 요청과 대체 처리

**사용자 스토리:** 사용자로서, 각 정책이 내 조건에 맞는 이유를 카드에서 확인하고 싶다.

#### 인수 조건

1. 찾기 실행 직후 각 매칭 정책 카드의 이유 영역은 초기 문구 `AI가 분석 중...`을 표시해야 한다.
2. `API_URL`이 비어 있지 않고 매칭 정책이 하나 이상이면 시스템은 추천 이유 API에 JSON POST 요청을 보내야 한다.
3. 추천 이유 요청 본문은 `{ mode: "explain", user, policies }` 구조여야 하며, `user`는 현재 사용자 조건이고 `policies`는 전체 매칭 정책 배열이어야 한다.
4. 추천 이유 API가 `{ results: [{ id, reason }] }`를 반환하면 시스템은 각 결과의 `id`를 같은 `id`의 정책 카드에 매핑하여 `reason`을 표시해야 한다.
5. `API_URL`이 빈 문자열이면 시스템은 추천 이유 API를 호출하지 않고 각 카드에 대체 추천 이유를 표시해야 한다.
6. 추천 이유 요청이 실패하거나, 응답 형식이 유효하지 않거나, 특정 정책 `id`의 결과 또는 `reason`이 누락되면 시스템은 해당 카드에 대체 추천 이유를 표시해야 한다.
7. 대체 추천 이유를 선택할 때 시스템은 먼저 해당 정책의 비어 있지 않은 `policy.reason`을 사용하고, 해당 값이 없으면 정확히 `나이·지역·소득 조건이 일치합니다`를 표시해야 한다.
8. 이유 영역의 배경색은 정확히 `#EEEAFB`여야 한다.

### 요구사항 7. 정책별 질문과 답변

**사용자 스토리:** 사용자로서, 관심 있는 정책에 대해 추가 질문을 하고 답변을 카드 안에서 확인하고 싶다.

#### 인수 조건

1. 각 정책 카드는 질문을 입력할 수 있는 컨트롤과 질문 전송 버튼을 제공해야 한다.
2. 각 정책 카드는 서로 다른 두 개의 예시 질문 컨트롤을 제공해야 한다.
3. 사용자가 예시 질문을 선택하면 시스템은 해당 예시 문구를 질문으로 사용하여 추가 전송 동작 없이 즉시 질문 API 요청을 시작해야 한다.
4. 사용자가 직접 입력한 비어 있지 않은 질문으로 전송 버튼을 실행하면 시스템은 질문 API 요청을 시작해야 한다.
5. 비어 있는 직접 입력 질문은 API로 전송하지 않아야 하며, 시스템은 질문 입력이 필요함을 한국어로 안내해야 한다.
6. `API_URL`이 비어 있지 않으면 질문 요청은 `{ mode: "ask", user, policy, question }` 구조의 JSON POST여야 하며, `user`는 현재 사용자 조건, `policy`는 해당 카드의 정책 객체, `question`은 전송한 질문이어야 한다.
7. 질문 요청을 기다리는 동안 시스템은 해당 카드의 답변 영역에 대기 상태의 말풍선으로 정확히 `답변 작성 중...`을 표시해야 한다.
8. 질문 API가 유효한 `answer`를 반환하면 시스템은 해당 답변을 성공 상태의 말풍선으로 표시해야 한다.
9. `API_URL`이 비어 있거나 요청이 실패하거나 응답의 `answer`가 누락되면 시스템은 해당 카드의 답변 영역에 정확히 `지금은 답변이 어려워요. 신청 페이지에서 확인해 주세요.`를 표시해야 한다.
10. 답변 말풍선의 배경색은 정확히 `var(--night)` 즉 `#26224A`여야 하고, 글자색은 정확히 `#F3F1FA`여야 한다.
11. 질문 요청 상태와 답변은 요청 대상 정책 카드에만 표시되어야 한다.

### 요구사항 8. 알림 토스트

**사용자 스토리:** 사용자로서, 알림 버튼을 눌렀을 때 동작이 접수되었다는 즉각적인 피드백을 받고 싶다.

#### 인수 조건

1. 사용자가 정책 카드의 알림 버튼을 실행하면 시스템은 정확히 `알림이 신청되었어요`라는 토스트를 표시해야 한다.
2. 알림 버튼은 실제 알림 등록, 저장, 외부 전송 또는 백엔드 요청을 수행하지 않아야 한다.
3. 토스트는 시각적으로 식별 가능하고 보조 기술이 상태 변화를 인지할 수 있는 라이브 영역으로 제공되어야 한다.
4. 토스트는 사용자 작업을 막지 않아야 하며 일정 시간 뒤 자동으로 사라져야 한다.

### 요구사항 9. 시각 디자인과 반응형 레이아웃

**사용자 스토리:** 모바일 사용자로서, 밝고 구분이 명확한 화면에서 입력과 결과를 편하게 이용하고 싶다.

#### 인수 조건

1. 시스템은 모바일 화면을 기본으로 설계하고 더 넓은 화면에서도 콘텐츠의 읽기 쉬운 너비와 간격을 유지해야 한다.
2. 시스템은 `:root`에 다음 CSS 사용자 지정 속성과 값을 문자 단위로 정확히 선언해야 한다.
   - `--ink:#1C1936;`
   - `--paper:#F6F4FC;`
   - `--card:#FFFFFE;`
   - `--violet:#6B4EF0;`
   - `--lime:#C8F169;`
   - `--muted:#57536F;`
   - `--line:#DDD7F3;`
   - `--night:#26224A;`
3. 시스템은 CSS 색상 값으로 순백 `#FFFFFF` 또는 `white`를 사용하지 않아야 한다.
4. 시스템은 CSS 색상 값으로 순검정 `#000000` 또는 `black`을 사용하지 않아야 한다.
5. 문서는 Noto Sans KR을 불러오는 정확한 Google Fonts 링크 `https://fonts.googleapis.com/css2?family=Noto+Sans+KR:wght@400;500;600;700;800&display=swap`를 포함하고, 기본 글꼴 모음에서 Noto Sans KR을 우선 사용해야 한다.
6. 화면은 헤더, pill 형태의 보조 문구, 강조 텍스트, 입력 폼, 찾기 CTA, 결과 숫자, 정책 카드, D-day 배지, 추천 이유 영역, 질문·알림 버튼, 답변 말풍선, 토스트를 시각적으로 구분해야 한다.
7. 주요 CTA와 상호작용 버튼은 배경과 충분히 구분되어야 하고, hover뿐 아니라 키보드 focus 상태를 제공해야 한다.
8. 텍스트와 상호작용 요소는 WCAG 2.1 AA 수준의 색상 대비를 목표로 해야 하며, 색상만으로 상태나 의미를 전달하지 않아야 한다.
9. 모바일 화면에서 폼 컨트롤, 카드, 버튼, 텍스트가 가로 스크롤이나 잘림 없이 표시되어야 한다.

### 요구사항 10. 한국어 UI, 접근성, 안전한 렌더링

**사용자 스토리:** 사용자로서, 보조 기술이나 키보드를 사용하더라도 안전하고 이해하기 쉬운 한국어 화면을 이용하고 싶다.

#### 인수 조건

1. 시스템은 사용자에게 보이는 레이블, 버튼, 상태, 오류, 빈 결과, 대기 및 실패 문구를 한국어로 제공해야 한다.
2. 문서의 주 언어는 한국어로 선언해야 한다.
3. 시스템은 의미에 맞는 제목 구조, `main`, `form`, `button`, 링크 등 시맨틱 HTML을 사용해야 한다.
4. 동적으로 변경되는 검색 결과 요약, 질문 상태, 토스트 중 사용자에게 즉시 알려야 하는 상태는 적절한 라이브 영역을 사용해야 한다.
5. 사용자 입력, `policies.json` 값, 추천 이유 API 응답 및 질문 API 응답은 안전한 DOM 렌더링 방식으로 표시해야 한다.
6. 시스템은 신뢰할 수 없는 데이터를 `innerHTML`, 인라인 이벤트 처리기 또는 동등한 HTML 실행 경로에 직접 삽입하지 않아야 한다.
7. 모든 기능은 마우스 없이 키보드만으로 실행할 수 있어야 한다.
8. API 또는 정책 데이터 처리 중 오류가 발생해도 시스템은 처리되지 않은 예외나 기술적인 오류 상세를 사용자 화면에 노출하지 않아야 한다.
