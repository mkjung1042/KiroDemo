# Implementation Plan

## Overview

이 계획은 `requirements.md`와 `design.md`를 따라 청년 정책 검색 프론트엔드를 순차적으로 구현하고 검증한다. 각 구현 작업은 선행 작업의 DOM, 상태, 렌더링 계약을 이어받으며 실제 앱 코드는 `frontend/index.html` 한 파일에서만 변경한다.

### 작업 원칙

- 실제 구현 변경은 오직 `frontend/index.html`에만 적용한다.
- HTML, CSS, JavaScript를 `frontend/index.html` 한 파일에 통합한다.
- `frontend/policies.json`, `lambda/handler.py`, 기타 소스 파일은 수정하거나 생성하지 않는다.
- 별도 테스트 파일, 테스트 설정 파일, 외부 라이브러리 파일을 추가하지 않는다.
- 각 작업은 앞선 작업이 완료된 뒤 순서대로 수행한다.
- 검증은 정적 검사와 브라우저 수동 동작 검사로 수행한다.

## Tasks

- [ ] 1. HTML/CSS/JavaScript 단일 파일 기반과 초기 데이터 구조를 구성한다
  - `frontend/index.html`에 `<!doctype html>`, `<html lang="ko">`, 문서 메타데이터, viewport, Google Fonts 링크, 내장 `<style>`, 시맨틱 `<body>`, 단일 `<script>` 구조를 만든다.
  - 헤더, 검색 `main` 영역, 검색 `form`, 결과 영역, 정책 목록, 토스트 라이브 영역의 기본 DOM을 구성한다.
  - 나이, 지역, 소득, 취업 상태, 주거 형태 입력과 한국어 레이블, 오류 표시 영역, 찾기 CTA를 구성한다.
  - `<script>`의 첫 JavaScript 선언을 문자 단위로 정확히 `const API_URL = "";`로 작성하고 그 앞에 다른 JavaScript 선언이나 실행문을 두지 않는다.
  - 설계에 정의된 필드를 모두 포함하는 정확히 3개의 객체로 `SAMPLE_POLICIES`를 선언한다.
  - `user`, `policies`, `matchedPolicies`를 관리할 앱 상태와 비동기 경합 제어용 revision·카드 참조·토스트 타이머 상태를 초기화한다.
  - DOM 참조 캐시, 이벤트 연결, 초기화 함수의 뼈대를 만들되 이후 작업에서 책임별 함수를 채울 수 있도록 구분한다.
  - **완료 기준:** HTML 문서의 주 언어가 한국어이고 주요 영역이 시맨틱 요소로 구성되어 있으며, 모든 폼 컨트롤에 연결된 레이블이 있다. 스크립트 첫 선언이 정확하고 `SAMPLE_POLICIES.length`가 3이며 각 샘플이 `id`, `name`, `minAge`, `maxAge`, `regions`, `maxIncome`, `employment`, `housing`, `benefit`, `deadline`, `url`을 포함한다. 변경된 구현 파일은 `frontend/index.html` 하나뿐이다.
  - _Requirements: 1.1, 1.2, 1.3, 1.4, 2.2, 2.3, 3.1–3.6, 3.8, 10.1–10.4_

- [ ] 2. 모바일 우선 UI와 디자인 시스템을 구현한다
  - `:root`에 요구된 8개 CSS 사용자 지정 속성을 문자 단위로 정확히 선언한다.
  - Noto Sans KR의 지정된 Google Fonts URL을 사용하고 기본 글꼴에서 `'Noto Sans KR'`을 우선한다.
  - 모바일 기본 한 열 레이아웃, 16px 수준의 좌우 여백, 최소 44px 상호작용 높이, 긴 텍스트 줄바꿈을 적용한다.
  - 넓은 화면에서 읽기 쉬운 최대 너비를 유지하고 768px 이상에서 폼과 결과 카드를 적절한 grid로 확장한다.
  - 헤더 pill, 강조 텍스트, 폼, CTA, 결과 수, 카드, D-day 배지, 이유 영역, 질문·알림 버튼, 답변 말풍선, 토스트의 시각적 계층을 정의한다.
  - 이유 영역 배경만 정확히 `#EEEAFB`로 지정하고, 답변 말풍선은 배경을 정확히 `var(--night)` 즉 `#26224A`, 글자색을 정확히 `#F3F1FA`로 지정하며, 임박 D-day에 `var(--lime)`을 사용한다.
  - 모든 상호작용 요소에 명확한 `:focus-visible` 상태를 제공하고 오류·대기·임박 상태가 텍스트로도 구분되게 한다.
  - `prefers-reduced-motion: reduce`에서 불필요한 전환을 제거한다.
  - **완료 기준:** `:root`에 `--ink:#1C1936;`, `--paper:#F6F4FC;`, `--card:#FFFFFE;`, `--violet:#6B4EF0;`, `--lime:#C8F169;`, `--muted:#57536F;`, `--line:#DDD7F3;`, `--night:#26224A;`가 정확히 존재한다. CSS에 `#FFFFFF`, `white`, `#000000`, `black`이 없고, 320px 이상 화면에서 고정 폭 때문에 가로 스크롤이 발생하지 않는 구조다. 키보드 포커스가 시각적으로 식별되고 주요 색 조합이 WCAG 2.1 AA 대비를 목표로 한다.
  - _Requirements: 5.5, 6.8, 7.10, 9.1–9.9, 10.7_

- [ ] 3. 정책 데이터 로드, 입력 검증, 다섯 조건 필터링을 구현한다
  - 초기화 시 이벤트를 먼저 연결하고 샘플 정책으로 검색 가능한 상태를 만든 뒤 `fetch("./policies.json")`를 실행한다.
  - 요청 거부, 비정상 HTTP, JSON 파싱 실패, 비배열, 빈 배열이면 `SAMPLE_POLICIES.slice()`를 사용하고, 비어 있지 않은 배열이면 해당 데이터를 채택한다.
  - 정책 로드 실패를 내부에서 처리하여 폼 입력과 검색을 중단하지 않고 기술 오류 상세를 화면에 노출하지 않는다.
  - `readAndValidateUser`, 오류 표시·해제 함수를 구현해 숫자 범위와 허용된 select 값 집합을 검증한다.
  - 유효하지 않은 제출은 검색을 중단하고 한국어 오류 요약, 필드별 `aria-invalid`, 설명 연결, 첫 오류 필드 포커스를 제공한다.
  - `matchesPolicy`와 `filterPolicies`를 DOM·네트워크와 분리된 함수로 구현한다.
  - 나이 범위, 전국 또는 선택 지역, nullable 소득 상한, 취업 상태 포함, 주거 형태 포함 조건을 모두 AND로 만족한 정책만 반환한다.
  - 유효한 검색마다 `state.user`, `state.matchedPolicies`, 검색 revision을 갱신하고 이전 결과를 새 결과로 완전히 교체할 준비를 한다.
  - **완료 기준:** 정책 파일의 모든 실패 유형에서 정확히 3개 샘플 정책으로 검색할 수 있고, 정상적인 비어 있지 않은 배열은 그대로 사용한다. 필수 입력 오류 시 필터나 API가 실행되지 않는다. 나이·지역·소득·취업·주거 중 하나라도 불일치하면 정책이 제외되며 경계 나이와 소득 상한은 포함된다. 연속 검색 시 상태가 마지막 유효 입력과 결과만 가리킨다.
  - _Requirements: 2.1, 2.4–2.6, 3.7, 4.1–4.8, 10.1, 10.8_

- [ ] 4. 결과 카드, D-day, 안전한 링크, 알림 토스트를 구현한다
  - 매칭 수를 별도 강조 요소에 넣은 한국어 결과 요약과 정책별 `article` 카드를 안전한 DOM API로 렌더링한다.
  - 결과가 0개이면 숫자 0을 포함한 요약을 표시하고 정책 목록은 비운다.
  - 카드에 정책 이름, 혜택, 마감일과 D-day, 정책 링크 또는 링크 불가 안내, 이유 영역, 질문 UI, 답변 영역, 알림 버튼을 배치한다.
  - 현재 로컬 날짜와 마감일을 UTC 자정 값으로 정규화해 달력 일수 차이를 계산하고 미래 `D-n`, 당일 `D-day`, 과거 `마감`, 잘못된 날짜 `마감일 확인 필요`를 표시한다.
  - 0일부터 7일까지 남은 정책에만 임박 클래스를 적용하고 `마감 임박` 텍스트를 함께 제공한다.
  - URL을 파싱해 `http:`와 `https:`만 링크로 만들고 새 창 링크에 `target="_blank"` 및 `rel="noopener noreferrer"`를 적용한다.
  - 카드 생성에는 `createElement`, `textContent`, `replaceChildren`, `DocumentFragment`를 사용하며 신뢰할 수 없는 값을 HTML, selector, element ID로 실행하거나 직접 삽입하지 않는다.
  - 알림 버튼은 네트워크·저장 없이 정확히 `알림이 신청되었어요` 토스트만 표시하고 약 3초 후 자동으로 숨긴다.
  - 토스트에 `role="status"`, `aria-live="polite"`, `aria-atomic="true"`를 적용하고 사용자 입력을 가로막지 않게 한다.
  - **완료 기준:** 카드 수와 순서가 매칭 배열과 일치하고 재검색 시 이전 카드가 남지 않는다. D-day 경계(0, 7, 8, 과거)와 잘못된 날짜가 설계대로 표시된다. 위험한 URL 스킴은 클릭 가능한 링크가 되지 않는다. 정책 값에 HTML 형태 문자열이 있어도 텍스트로만 보인다. 알림 버튼은 정확한 토스트 외 부수 효과가 없다.
  - _Requirements: 4.8, 5.1–5.7, 6.1, 7.1–7.2, 8.1–8.4, 10.3–10.6, 10.8_

- [ ] 5. 추천 이유 explain API와 정책별 fallback을 구현한다
  - 카드가 처음 렌더링될 때 각 이유 영역에 정확히 `AI가 분석 중...`을 먼저 표시한다.
  - `API_URL.trim()`이 비어 있지 않고 매칭 결과가 있을 때만 explain 요청을 한 번 보낸다.
  - JSON POST 본문을 `{ mode: "explain", user, policies }` 구조로 만들고 `policies`에 전체 매칭 정책 배열을 전달한다.
  - 응답의 `results`를 정책 `id` 기준으로 매핑하고 비어 있지 않은 문자열 `reason`만 해당 카드에 표시한다.
  - URL 미설정, HTTP·네트워크·파싱 실패, 잘못된 응답 형식, 누락된 ID·reason에는 정책별 fallback을 적용한다.
  - fallback은 비어 있지 않은 `policy.reason`을 우선하고 없으면 정확히 `나이·지역·소득 조건이 일치합니다`를 사용한다.
  - 검색 revision을 확인해 이전 검색의 늦은 응답이 최신 카드 내용을 덮어쓰지 않게 한다.
  - 모든 API 응답은 `textContent`로 렌더링하고 예외나 원시 서버 응답을 사용자에게 노출하지 않는다.
  - **완료 기준:** 빈 `API_URL`에서는 explain fetch가 호출되지 않고 모든 카드가 올바른 fallback으로 전환된다. 설정된 URL에서는 요청 본문이 계약과 일치하고 결과 순서와 무관하게 ID별 이유가 표시된다. 부분 응답은 누락 카드에만 fallback을 적용하며 재검색 전 응답은 무시된다.
  - _Requirements: 6.1–6.8, 10.5, 10.6, 10.8_

- [ ] 6. 정책별 ask 상담, 비동기 상태, 오류 처리를 구현한다
  - 각 카드에 서로 다른 예시 질문 버튼 두 개와 연결된 레이블이 있는 직접 질문 입력·전송 폼을 완성한다.
  - 결과 영역 이벤트 위임으로 예시 질문 클릭, 질문 폼 제출, 알림 버튼 동작을 처리하고 카드 인덱스를 정수 및 범위로 검증한다.
  - 예시 질문을 선택하면 해당 문구를 입력에 반영하고 추가 전송 없이 즉시 ask 흐름을 시작한다.
  - 직접 질문을 trim한 결과가 비어 있으면 fetch 없이 해당 카드에 `질문을 입력해 주세요.`를 표시한다.
  - 질문 시작 시 해당 카드의 답변 영역에 `답변 작성 중...` 대기 말풍선을 표시한다.
  - `API_URL.trim()`이 비어 있지 않을 때 `{ mode: "ask", user, policy, question }` 구조의 JSON POST를 보낸다.
  - 유효한 비어 있지 않은 문자열 `answer`는 성공 말풍선에 표시하고, URL 미설정이나 요청·응답 오류에는 `지금은 답변이 어려워요. 신청 페이지에서 확인해 주세요.`를 표시한다.
  - 카드별 answer revision과 노드 참조로 요청 상태와 답변을 대상 카드에만 반영하고 같은 카드의 오래된 응답이 최신 응답을 덮지 않게 한다.
  - 답변 영역을 `aria-live="polite"`로 제공하고 대기·성공·실패를 한국어 텍스트로 식별 가능하게 한다.
  - **완료 기준:** 예시 질문은 한 번의 클릭으로 즉시 요청 흐름을 시작하고 직접 질문은 Enter와 버튼으로 제출된다. 빈 질문은 API로 전달되지 않는다. 요청 본문은 현재 사용자, 대상 정책, 전송 질문을 정확히 포함한다. URL 미설정과 모든 실패 유형은 고정된 한국어 오류를 대상 카드에만 표시하며 다른 카드 상태를 바꾸지 않는다. 연속 질문에서는 마지막 요청 결과만 남는다.
  - _Requirements: 7.1–7.11, 10.1, 10.4–10.8_

- [ ] 7. 최종 정적 검증과 브라우저 동작 검증을 수행한다
  - Git 변경 목록으로 구현 변경이 `frontend/index.html` 하나에만 한정되었는지 확인한다. 계획 문서인 `.kiro/specs/youth-benefit-frontend/tasks.md` 외 다른 파일 변경이 없어야 한다.
  - 첫 JavaScript 선언, 정확한 `API_URL`, 샘플 정책 3개, CSS 토큰 8개, Google Fonts URL, 이유·답변 배경색을 정적으로 확인한다.
  - 금지 색상과 `innerHTML`, `insertAdjacentHTML`, `document.write`, 인라인 이벤트 처리기가 없는지 확인한다.
  - 모든 입력 레이블, 시맨틱 제목 구조, `main`·`form`·`button`·링크, 라이브 영역, 포커스 스타일을 확인한다.
  - 브라우저에서 정책 로드 성공과 fallback, 유효·무효 입력, 다섯 조건 경계, 0개 및 여러 개 검색 결과, 연속 검색 결과 교체를 검증한다.
  - D-day의 과거·당일·7일·8일·잘못된 날짜, 안전·위험 URL, 알림 토스트 자동 숨김을 검증한다.
  - API 미설정 상태와 개발자 도구의 fetch 대체를 이용해 explain ID 매핑·부분 fallback·오래된 응답 무시, ask 대기·성공·실패·카드 격리를 검증한다.
  - 320px, 375px, 768px, 1024px viewport에서 가로 스크롤과 잘림을 확인하고 키보드만으로 전체 검색·링크·질문·알림 흐름을 실행한다.
  - 정책과 API 응답에 HTML 형태 문자열을 넣어 추가 DOM이나 스크립트가 생성되지 않고 보이는 텍스트로만 렌더링되는지 확인한다.
  - 별도 테스트 파일이나 테스트 설정을 생성하지 않고 발견된 결함은 `frontend/index.html`에서만 수정한 뒤 관련 검증을 반복한다.
  - **완료 기준:** 요구사항 1–10의 모든 인수 조건이 정적 검사 또는 브라우저 동작 검사로 확인되고 처리되지 않은 예외, 기술 오류 노출, 키보드 차단, 320px 이상 가로 넘침이 없다. `frontend/index.html` 외 구현 파일과 별도 테스트 파일은 생성·수정되지 않았다.
  - _Requirements: 1.1–1.4, 2.1–2.6, 3.1–3.8, 4.1–4.8, 5.1–5.7, 6.1–6.8, 7.1–7.11, 8.1–8.4, 9.1–9.9, 10.1–10.8_
